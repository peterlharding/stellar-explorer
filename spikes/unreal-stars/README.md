# Unreal spike: the catalogue in Unreal Engine 5.8

A throwaway project that answers one question before ADR 0007 (Godot) is reconsidered: can Unreal Engine render the Stellar Explorer catalogue well, on the desktop, the HTC Vive Pro 2 and the Apple Vision Pro?
It is not the app; the app will live in `src/app/` once the engine is decided.

## How it is built

- **C++ only.** No Blueprints and no map of its own: the game mode spawns the star field into the engine's empty `Entry` map.
- **No committed binary assets.** The one material is generated by `Scripts/make_star_material.py` from the HLSL in `Shaders/`, so what is reviewed and diffed is text. `Content/Generated/` is git-ignored.
- **Brightness from physics, in the shader.** Each star is four vertices at its position. The material computes its apparent magnitude from its absolute magnitude and its distance from the camera, and from that the sprite's size and brightness. `LimitingMag` (6.5) is the faintest star meant to be visible. Colour is a blackbody at the star's temperature.
- **Data straight from `data/catalogue.sqlite`**, through the engine's SQLite plugin, using the `star` view.

```sh
./spike.sh build          # compile the editor target (about 30 s)
./spike.sh material       # generate the star material
./spike.sh run            # fly: WASD and mouse
./spike.sh measure        # circle the Sun for 30 s, log frame times, screenshot
./spike.sh look 5.6,2     # screenshot the sky from the Sun towards RA 5.6 h, Dec +2°
```

## Results

### Part 1: desktop, Mac (28 October 2026)

M1 Max, macOS 27.0.1, Unreal Engine 5.8.4, Xcode 27.1, window 1600×900.

- **Loads and renders the catalogue.** 113,012 stars (every star with a position and an absolute magnitude) load from SQLite in 3.2 s.
- **Correct sky, to the pixel.** Seen from the Sun towards Orion (`./spike.sh look 5.6,2`), Betelgeuse, Rigel, Sirius, Procyon and Aldebaran each land within a few pixels of where a gnomonic projection of their catalogue positions puts them, the right way round. This checks the conversion from the catalogue's right-handed ICRS frame to Unreal's left-handed one. Colours follow the spectral types: Betelgeuse and Aldebaran orange, Rigel and Sirius blue-white.
- **Fast.** Circling the Sun at 6 pc, the frame rate holds the display's 120 Hz: median frame 8.33 ms, 99th percentile 9.9 ms (deferred) and 9.2 ms (forward shading with 4× MSAA, as the headsets will use). GPU time is 6.0 ms median; the game thread 1.3 ms. With no stars at all, GPU time was 7.8 ms, because the GPU clocks down under a lighter load: the stars' cost is below the noise, and the time is Unreal's fixed deferred-rendering cost.
- **Startup hitch.** One frame of about 400 ms in each run, while shaders compile on first use. A packaged build compiles them ahead of time.

Problems met and fixed on the way, worth knowing for the real app:

- Unreal's SQLite wrapper asserts if a database object is destroyed while still open.
- The player's pawn is spawned while the map loads, before `StartPlay`, so command-line options must be read in `InitGame`.
- The free-flying pawn takes mouse movement the moment the window opens; scripted views must hold their direction every frame.
- A pawn without its own camera component is viewed at a field of view other than the one reported; give the pawn a camera.
- Enabling the OpenXR visionOS plugin before the visionOS platform component is installed stops the editor from starting ("Missing Modules: OXRVisionOSSettings"). It is enabled once that component is in.

### Part 2: Vision Pro (runs in full immersion)

Getting there took eight fixes, recorded with their evidence in [VISIONOS.md](VISIONOS.md).
The ones that matter for the real app: package with `-pak`; start the engine from `VisionOSStartup.cpp`, because the launcher engine's scene lifecycle never starts in a SwiftUI app; override the Vision Pro device profile's `r.Mobile.XRMSAAMode`; keep SQLite's temporary tables in memory; and declare the tracking usage descriptions in `Info.plist`.


- **Platform files.** The iOS and visionOS target platforms are optional downloads in the Epic Games Launcher (the engine's Installation Options, Target Platforms; visionOS requires iOS). The launcher will not change an engine while any of its editors is running: it defers the install silently, so close every Unreal Editor first.
- **Toolchain.** With the OpenXR visionOS plugin enabled, the spike compiles and links for visionOS with Xcode 27.1 and the visionOS 27.0 SDK, although Unreal 5.8 states only "Xcode 15.3 or later". The build then stops at signing, which needs the developer's team in `Config/UserEngine.ini` (`[/Script/MacTargetPlatform.XcodeProjectSettings]`, `CodeSigningTeam=`).
- **Still to see:** frame rate, comfort, and how the stars look.

### Part 3: HTC Vive Pro 2 on Windows (not started)

## Still to judge

- Stars look right but are understated: the brightest stars need a bloom or glare that reads as brilliance, and the exposure wants tuning in a headset, not on a monitor.
- Ready for the headsets, untested in them: the pawn's camera follows the headset, and in a headset the view starts 1.5 m from the Sun at 1 pc to 1 m, so α Centauri is 1.3 m away. Forward shading, MSAA, instanced stereo and mobile multiview are on; `Config/VisionOS` and `Config/Windows` start the app in VR; the catalogue is staged into packages as a plain file.
